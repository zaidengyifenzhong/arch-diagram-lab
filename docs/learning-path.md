# 给体系结构新生的读图与画图路线

这份课程服务于**你自己理解和表达系统**，不要求使用 AI，也不要求会编程。纸笔、幻灯片工具、矢量编辑器都能完成。先把一张图讲清楚，再学习自动生成。先后只是教学步骤，不意味着颜色、线宽等语义编码可以等到美化时才决定。

这里讨论架构、机制、流程和设计对比图，**不包含实验结果曲线或性能柱状图**。下述流程与检查项是本项目的教学建议，不是所有会议或论文共同遵守的强制标准。具体投稿格式应查对应会议当年的官方指南；不要把某篇论文的配色当作行业规范。

## 0. 先知道你在学什么

一张好的机制图是一个经过取舍的解释，而不是系统的缩小照片。

- **读者问题**：读完图后应该能回答哪一个问题？例如“谁决定下一个事件？”
- **实体**：需要出现的对象，如队列、调度器、资源状态。实体也可能是阶段、线程、状态或数据结构，并不一定是硬件。
- **关系**：实体之间发生什么，如传递请求、发出选择、包含、读取状态、先后执行。
- **抽象层级**：这张图解释模块职责、一次请求，还是单个结构的内部状态？不要未经说明混在一起。
- **语义**：盒子、箭头、虚线、颜色、边界分别“表示什么”。
- **布局**：语义确定后，把对象放在哪里、如何对齐、如何绕线。

**关键判断：**交换两个盒子的位置，如果系统解释不变，改的是布局；把箭头反向、把“请求”改成“完成”、把软件模块放进标为“芯片”的边界，可能已经改变语义。

## 先回答你真正关心的：成熟 researcher 的图有什么不同？

不是“用了某套顶会配色”，而是**知道读者此刻需要看见什么，以及哪些细节应该暂时不看见**。判断成熟度，可以先问三个问题：

1. **什么可以删，而不损害这张图要支持的主张？**重复实例可以压缩，但负责说明规模的倍数或省略标记可能必须保留。
2. **什么必须保留，即使让图不那么简洁？**关键依赖、抽象边界、入口出口、对比基准不能为了留白而消失。
3. **若把这条箭头画错，读者会误解什么？**如果答不出，可能尚未理解关系；如果会改变控制权、状态依赖或数据归属，它就是需要优先审查的语义。

本项目已核验的种子图给出几种不同的选择，而不是一种统一外观。下面是对 `corpus/figures.json` 核验记录的教学归纳；**只有三篇九图，不能据此宣称“所有知名实验室都遵循这些潜规则”**。

| 对照读图 | 你应留意的专业判断 | 可以借鉴什么，而不是照抄什么 |
|---|---|---|
| [FireSim 图1与图2，PDF第3页](https://sagark.org/assets/pubs/firesim-isca2018.pdf#page=3) | 目标网络拓扑与执行它的宿主映射分开解释；图2边界与倍数标记提供实现层次 | 遇到“被模拟对象”和“运行模拟的机器”，先区分两个抽象层，不急着揉成一个大框图 |
| [Ray 图4，PDF第6页](https://www.usenix.org/system/files/osdi18-moritz.pdf#page=6) 与 [图6，第8页](https://www.usenix.org/system/files/osdi18-moritz.pdf#page=8) | 图4用不同边型区别依赖；图6的线宽被图注赋予请求率含义 | 先读视觉编码的语义，再决定能否简化；不能“统一美化”为全部同粗实线 |
| [AIFM 图4，PDF第5页](https://www.usenix.org/system/files/osdi20-ruan.pdf#page=5) 与 [图5，第8页](https://www.usenix.org/system/files/osdi20-ruan.pdf#page=8) | 表示格式需要位号与对齐基准；组织结构可以接局部对象放大 | 贡献涉及位域就画格式，涉及多尺度组织就分尺度；不是所有机制都适合流程箭头 |

项目现有范围已扩展为**六篇十八图**：上述三篇九图仍称“种子组”；另有 Eyeriss、RowClone、Plasticine 三篇九图，见 [架构论文对照](../corpus/expert-comparisons.md)；两组结论与反例见 [跨组复核](../corpus/synthesis-review.md)。新增样本反驳了几条容易误学的死规矩：Plasticine 的局部图先于芯片总览，说明论文不必先总览；RowClone 与 Eyeriss 的关联放大说明一图可以有多个明确关联的尺度；密集 datapath 也可能是解释所需，并非“框越少越专业”。六篇仍是有目的的小样本，不是领域普查。

从这些样本可练习的共同判断是：**视觉形式服从所解释的关系，细节数量服从论点，比较与边界有明确基准。**这是基于小样本的可检验启发，不是审稿人打分公式。图的质量也不能从作者出身推断；要检查它是否让读者准确理解贡献。

学习时，先做一次上述真实图对照，再做最小合成练习验证理解，最后回到论文。合成例子只是把复杂度降下来，不是课程的最终审美目标。

## 1. 先选图，再选工具

| 你希望读者回答的问题 | 优先尝试的图 | 必须交代 | 不应暗示 |
|---|---|---|---|
| 系统由谁组成，谁与谁交互？ | 系统总览 / 模块图 | 模块职责、边界、关键接口 | 盒子大小就是面积；位置就是物理距离 |
| 一次操作如何完成，谁等待谁？ | 机制流程 / 编号步骤图 | 起点、顺序、条件、状态变化 | 每一段长度就是持续时间 |
| 多个参与者如何交换消息？ | 泳道 / 时序示意 | 参与者、时间方向、消息、等待 | 没有标尺仍能读出精确时延 |
| 设计改动在哪里？ | 前后 / 基线与方案对比 | 对齐的比较对象、不变量、变化点 | “之后”自然更快或更正确 |
| 某结构内部如何组织？ | 结构放大 / 状态示意 | 条目含义、索引、状态或字段 | 一张结构示意能替代完整算法 |

这些不是互斥的论文图类别，也不是必须凑齐的清单。总览可能加一个小型机制面板；但每个面板仍要有自己的读者问题。如果“所有问题都要回答”，先拆图。

## 2. 推荐学习顺序：六次短练习

时间只作安排参考，达到验收标准比按时结束更重要。对应题目见 [exercises.md](exercises.md)。

| 次序 | 任务 | 交付物 | 进入下一步的标准 |
|---|---|---|---|
| 1，约 20 分钟 | 用一句话读懂一张图 | 问题、结论、三个不能推断的事实 | 不依赖颜色也能复述主要关系 |
| 2，约 30 分钟 | 从机制文字抽取语义 | 实体表、关系表、假设与编码清单 | 每条关系都有方向和含义，未知项未被编造 |
| 3，约 20 分钟 | 规划论文需要哪些图 | 三张图的“问题—结论—范围”卡片 | 三张图不是同一幅总览的换皮 |
| 4，约 40 分钟 | 只用黑白画灰稿 | 一张可讲解的总览和一张机制草图 | 别人能沿线读懂，不需要你补解释 |
| 5，约 25 分钟 | 精调已确定的视觉编码 | 图例核对、文字与线条参数、最终尺寸预览 | 去色后仍能区分关键关系；缩小后可读 |
| 6，约 30 分钟 | 独立评审与修订 | 一版修订图及三条修改理由 | 先修语义错误，再修拥挤与美观 |

先浏览上面的真实图对照，再用原创练习练基本判断，完成后回到真实论文做深入分析。不要一开始就临摹复杂论文的所有细节：临摹会训练排版，但不一定训练“为什么放这个盒子”。

## 3. 如何读一张陌生论文图

按以下顺序做笔记；不要凭缩略图猜机制。

1. **读图题、图注和正文引用该图的段落。**写下作者想支持的一个主张。
2. **找图的边界。**有哪些面板？同一个盒子在不同面板是否代表同一个对象？大框是逻辑分组、软件进程、设备还是节点？未说明就标为待核实。
3. **列实体。**把原文术语原样记下，再用自己的话写职责。不会的缩写先查定义，不要靠图形猜。
4. **逐条读边。**写成“源 → 目标：传递 / 控制 / 返回什么”。双向线可能是双向通信，但不一定代表两方向消息完全相同。
5. **找路径或变化。**沿一次操作讲一遍，或说明左右面板改变了哪项职责；遇到断点回查正文。
6. **记录省略。**错误处理、队列细节、并发请求、资源争用是否画出？没画出不等于系统没有。
7. **复述并自测。**遮住论文，用 60 秒说明问题、主要关系和一个限制。然后对照正文纠正，而不是凭记忆补齐。

论文阅读卡可手写：

```text
论文 / 图号 / 页码：
图题与正文定位：
它回答的问题：
原文直接支持的结论：
实体与关系：
符号解释的证据（图例 / 图注 / 正文）：
我的推测（尚未证实）：
不能从图中推出的内容：
我愿意借鉴的表达方式及原因：
```

只有在项目 `corpus/` 中有实际原图定位、来源和核验记录时，才把论文案例用于上述练习。本文不预先替尚未核验的论文图填写内容，也不把复述或重绘称为原论文图。

## 4. 如何从文字走到图：一个完整的小例子

本项目的 **AsterSim 是简化的原创教学系统，不是论文实验系统，也不是研究图的统一模板**。生成图的横幅 `SIMPLIFIED SYNTHETIC TEACHING EXAMPLE · NOT A RESEARCH TEMPLATE` 明确了这一用途。先看 `examples/01-overview.json` 的问题和关系，再查看对应生成图；JSON 是练习答案来源，不是你学习画图的前置条件。

### A. 先写问题和范围

问题：“事件数据、调度决策和资源完成反馈在哪里相遇？”

范围：“模块交互总览；不解释策略算法、所有资源状态更新或每一步的时间。”

### B. 抽实体，不急着画框

| 实体 | 本图中的职责 | 不应擅自推断 |
|---|---|---|
| Trace input | 提供事件输入 | 文件格式、硬件端口 |
| Event queue | 承载待处理事件 | 队列深度、FIFO 保证 |
| Scheduler | 发出选择控制 | 采用何种调度算法 |
| Execution engine | 接收事件与选择，发出资源请求 | 具体流水级或处理器数量 |
| Resource model | 接收请求，发出完成反馈 | 必定对应一块物理芯片 |
| Policy state | 提供策略相关信息 | 如何存储、何时更新 |

### C. 先写关系，再排版

- Trace input → Event queue：events，数据。
- Event queue → Execution engine：next event，数据。
- Execution engine → Resource model：resource request，数据。
- Scheduler → Execution engine：select，控制。
- Resource model → Scheduler：completion feedback，反馈。
- Policy state → Scheduler：policy，控制信息。

数据、控制、反馈是**本示例的分类选择**。其他论文可能把完成消息也归为数据；重要的是局部定义清楚且一致。

### D. 先确定编码含义，灰稿验证后精调样式

在关系表阶段就决定哪些区别需要编码；若颜色或线宽表示角色或数量，它们的含义此时已经是语义的一部分。灰稿可以先以文字、线型替代色值以验证可读性；“最后着色”只指精调色值，不是最后才决定颜色代表什么。

先把输入、队列、执行、资源按主要读取方向安排，把策略与调度放在旁边；这只是易读布局，不代表物理位置。每条边先保留文字。回路较长时沿外围绕行，避免穿过盒子；不要为了让图“对称”删除反馈。

现在做三个检查：读者能找到选择来自谁吗？完成反馈回到谁？单凭图能否误以为调度器直接承载全部事件数据？若有误解，先改标签和连接，别先换配色。

## 5. 风格：先建立本图的语言，再谈“像论文”

没有一种配色能让图自动成为体系结构论文图。本项目建议使用节制且可解释的视觉语言：

- 同一对象跨图尽量同名；缩写首次出现时解释。图中标签短，完整含义写入图注。
- 同一图中同一种关系使用一致线型和箭头；跨图若语法改变，应重新说明，而非强求一种箭头永久只有一种含义。不同关系可用标签、线型及颜色冗余编码。虚线没有脱离上下文的固定含义。
- 填充色只承担清楚的任务，例如区分数据与控制，或突出新增模块；不要用彩虹色装饰每个盒子。
- 若靠颜色表达变化，同时使用文字“新增”、边框或面板标题。灰度后丢失信息，就还没有完成。
- 对齐、留白、层级和路由服务于阅读顺序；不必每个模块等宽，但大小不要无意暗示容量或重要性。
- 在**实际放入论文的尺寸**检查文字、箭头尖端、细线与标签间距，而不只看放大的编辑画布。字体尺寸、文件格式等最终服从目标出版要求。
- 图注交代“看什么、符号是什么、没有声称什么”。图注不应成为为无标签箭头补洞的长说明。

## 6. 新生常见误区与纠正

| 误区 | 为什么危险 | 最小修复 |
|---|---|---|
| 箭头就是“有关系” | 无法知道流向、载荷或先后 | 写出动词或消息名，必要时拆成两条边 |
| 每个盒子是一块芯片 | 混淆软件、逻辑模块与部署 | 标明抽象层和边界含义 |
| 总览必须包括实现的一切 | 核心论点被细节淹没 | 将细节移入机制图或放大图，并注明省略 |
| 从左到右就表示精确时间 | 布局变成伪测量 | 标注“概念顺序，非按时间比例” |
| 红色天然表示瓶颈 | 颜色约定不是跨论文通用的 | 查图例或给出本图定义 |
| 线交叉必定表示连接 | 可能只是路由相交 | 使用连接点或绕行，说明连接规则 |
| AFTER 看起来更简洁，因此更快 | 结构变化不等于性能证据 | 结论限于职责变化，不写加速比 |
| AI 画得整齐就机制正确 | 排版不会证明关系真实 | 先审实体与关系表，再审生成图 |

## 7. 最终你应具备的能力

你不必记住某篇论文用了几种蓝色。你需要能独立：选择图型；解释每个符号；指出省略与假设；从机制文字建立关系表；画出可读灰稿；把一条评审意见转成具体修改。最后再考虑让工具自动摆放和复用样式。工具能节省重复劳动，不能代替你的语义判断。
