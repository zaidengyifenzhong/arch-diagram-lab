# 动手练习：从机制文字到能被别人读懂的图

配套阅读：[learning-path.md](learning-path.md)。你可以全程用纸笔完成。建议每题先独立做，再看答案；下面的答案是**原创 AsterSim 教学设定**，不是论文结论，也不代表唯一合法布局。

每次修订保留前一版，用一句话写明“改了什么，防止哪种误读”。不要只记录“更美观”。

## 练习 1：不画图，先划清知道与不知道（15–20 分钟）

### 题目

教学设定：

> Trace input 向 Event queue 提供事件；队列把 next event 交给 Execution engine。Scheduler 向执行引擎发送 select 控制，选择依据包含 Policy state 提供的 policy。执行引擎向 Resource model 发出 resource request；资源模型向调度器返回 completion feedback。

交付：

1. 用一句话写这张总览图回答的问题。
2. 列六个实体及六条有向关系，关系写明内容。
3. 把下面六句话标成“设定支持 / 不足以判断”：
   - 队列容量为 64。
   - 调度器控制执行引擎的选择。
   - 资源模型是一颗独立芯片。
   - 资源模型的完成反馈到达调度器。
   - 每个事件需要 10 ns。
   - Policy state 如何更新已由这段话说明。

### 参考答案

- 问题可写：“事件数据、调度决策和资源完成反馈如何连接？”不要写“该系统能加速多少”。
- 六个实体就是设定中的六个命名对象。
- 六条边：输入 → 队列（events）；队列 → 执行引擎（next event）；调度器 → 执行引擎（select）；策略状态 → 调度器（policy）；执行引擎 → 资源模型（resource request）；资源模型 → 调度器（completion feedback）。
- 六句话依次：不足以判断、支持、不足以判断、支持、不足以判断、不足以判断。

**修订门槛：**少一条边、反向一条边或把未知细节当事实，都先回改语义表。暂不评分配色与位置。

## 练习 2：决定论文需要哪些图（20 分钟）

### 题目

假设你要介绍这个教学系统的三件事：系统职责、一次成功调度的步骤、把调度策略从整体模拟器中分离出来的设计变化。请设计三张“图卡”：

```text
图型：
读者问题（一句）：
看完应带走的结论（一句）：
必画实体 / 关系：
明确省略：
不能靠这张图证明：
```

### 参考答案与判分点

| 图卡 | 问题与核心结论 | 省略 / 不能证明 |
|---|---|---|
| 总览 | 数据路径、选择控制、反馈在哪里相遇？三种关系应区分 | 不展开策略算法；不能证明吞吐量 |
| 机制 | 一次成功执行前后经历什么？入队 → 选择 → 预留 → 执行 → 释放 | 暂不画失败重试；不能把横向距离读为时间 |
| 前后对比 | 策略分离改变了哪项职责边界？策略成为显式模块 | 不画所有系统组件；不能证明加速或开销降低 |

不要求措辞相同。若三张图都只列模块、没有步骤或变化，就是重复信息，应重做图卡。

## 练习 3：总览灰稿与“只改布局”挑战（30–40 分钟）

### 题目

用练习 1 的语义表画总览，仅使用黑、白、灰；每条箭头带标签。先不要看生成图。

再画第二版：把主路径从横向改成纵向，保留所有实体、方向和标签。两版必须表达同一系统。最后找一位同学，或自己遮住设定，只看图回答：

1. 谁发出 select？
2. completion feedback 回到哪里？
3. policy 与 events 是同一种信息吗？
4. 哪些对象的物理位置仍未知？

### 参考答案

1. Scheduler。
2. Scheduler，不是直接回到 Event queue。
3. 这张教学图把它们分别作为控制信息与事件数据表达；不要只用颜色说明差异。
4. 全部对象的物理部署位置都未由该总览确定。

可以采用“输入—队列—执行—资源”主路径，另放“策略状态—调度器”，用外围回线连接资源反馈。纵向版同样正确。**答案不在盒子的坐标里。**核对来源：`examples/01-overview.json`。

**修订门槛：**两版边集合一致；无穿过文字的边；箭头终点明确；改变位置未改变“包含于哪个边界”。如果删边才能画整齐，说明需要重新路由或拆面板，而不是删机制。

## 练习 4：机制顺序不等于时间测量（30 分钟）

### 题目

新增教学设定：

> 一次成功调度依次经过 Enqueue、Select、Reserve、Execute、Release。Enqueue 向 Select 传递 ready event；Select 向 Reserve 传递 selection（选择控制）；Reserve 获得 Capacity state 的 available slots 信息，并在成功后向 Execute 给出 grant；Execute 向 Release 传递 completion；Release 向 Capacity state 返回 return slot。

交付：

- 画五个编号阶段和 Capacity state。
- 给每条边写标签；图注写明“成功路径、概念顺序，非按时间比例”。
- 找出两项设定没有解释、但完整实现可能需要说明的事项。
- 回答：如果 Reserve 得不到资源，能否直接从图中断言它会丢弃事件？

### 参考答案

主链是五个阶段，另有 Capacity state → Reserve（available slots）与 Release → Capacity state（return slot）。这些盒子表示阶段与状态，不是五颗处理器。

两个合理的缺口：预留成功如何更新 / 扣减容量状态；资源不足时等待、重试或其他处理如何执行。原始教学图没有完整描述这些细节；把缺口标出来比自行补出“真实实现”更好。

不能断言会丢弃事件；设定只描述成功路径。若你要扩展成含失败分支的图，必须先新增并显式标注教学假设，例如“资源不足则等待后重试”，而不是声称原示例已经如此定义。

核对来源：`examples/02-mechanism.json`。边角色也要看载荷：`selection` 在本示例表示选择控制；边的类别应按关系含义判断，而不是按两个端点的左右位置判断。

**修订门槛：**成功顺序、授权条件及释放反馈可读；不写未经给出的持续时间；读者知道没有展示完整状态机。

## 练习 5：前后对比，克制你的结论（25 分钟）

### 题目

Before：Events → Monolithic simulator。

After：Events → Execution engine；Scheduling policy → Execution engine（select event）。

画两面板对比，让共同输入容易对应，新增显式策略模块容易找到。禁止加入加速比、延迟曲线或“更快”标签。写两句话图注：一句结论，一句范围限制。

### 参考答案

可用同名、相近位置的 Events 帮助对应；After 中显式标出 Scheduling policy 的职责，而不是只让它变成另一种颜色。示例答案：

> 策略职责从整体模拟器中分离为显式的 Scheduling policy 模块，由其向 Execution engine 发出选择控制。此图只比较职责分解，不表示完整接口集合或测得的性能收益。

生成图将新出现的显式模块标为 `Scheduling policy [NEW]`；`[NEW]` 指这里的职责分解变化，不声称新增调度能力或物理硬件。

Before 中没有独立策略盒子，**不等于 Before 没有调度策略**；可能只是职责耦合在整体模块内。After 多了一个盒子，也不意味着多了一台机器。核对来源：`examples/03-before-after.json`。

**修订门槛：**读者能指出“改变的是什么”和“不变的是什么”；左右面板没有借助不一致的输入名或缩放制造误导。

## 练习 6：核对编码、精调样式，但不改变语义（20–30 分钟）

### 题目

选择练习 3 或 4，检查并补齐在语义阶段确定的、仅用于本图的视觉字典。若之前没有确定，请先修订语义方案，再渲染；不要把有技术含义的颜色或线宽视为事后装饰：

```text
实体形状表示：
边界表示（若没有，写无）：
数据边：
控制边：
反馈边：
强调色表示：
交叉线是否连接：
```

先做灰度版本，再加最多少量强调色；不要求固定颜色数量。将图缩到实际使用宽度，看文字与线条。检查去掉所有颜色后，能否仍回答前三题。

### 参考答案

一种可行方案：实体用矩形并用文字区分职责；数据用实线加载荷标签，控制用虚线加控制标签，反馈沿外围并标 completion / return slot；强调色只突出本图讨论的对象。也可以用其他组合，条件是图例定义、逐边一致、黑白仍可读。

这不是通用标准：虚线在其他论文中可能表示可选路径、逻辑边界或尚未发生的操作。不得在阅读陌生图时套用本题字典。

**修订门槛：**样式前后关系表完全不变；每种非装饰性视觉编码能被解释；图例与图中实际使用一致。仅把所有盒子涂成不同颜色，不算完成。

## 练习 7：评审一张“漂亮但错了”的图（20 分钟）

### 题目

假设某图有如下问题，按“先修语义，再修阅读，再修装饰”排序，并写具体修改：

- A. completion feedback 被画到 Event queue。
- B. 紫色用于三个互不相关的含义，没有图例。
- C. 图下写着“阶段等宽，所以耗时相等”。
- D. 一个箭头穿过 Scheduler 的文字。
- E. 总览标题只是“Architecture”。
- F. AFTER 面板标着“2× faster”，却没有实验或依据。

### 参考答案

先处理 A、C、F：A 改回 Resource model → Scheduler；C 删除错误解释，注明概念顺序不按时间比例；F 删除无依据性能结论。B 若已导致关系含义歧义，也属语义优先级，应重新定义编码。随后修 D 的路由、改 E 为具体问题或核心主题。A/C/F 内部的先后顺序不是考试重点；不能为了配色先忽视错误机制。

## 练习 8：把方法迁移到一张真实论文图（30–45 分钟）

从项目 `corpus/` 中选择**已有原图来源和核验定位**的一张图。只读它的原图、图注和对应正文，填写学习路线中的阅读卡。不要用本文的合成例子答案替代原论文。

交付：一张阅读卡、一份实体关系表、一个不冒充原图的“我自己的理解草图”，以及至少一个回查正文后修正的误解。如果没有发生误解，可写一个经过核实的疑点，不要编造学习经历。

**验收：**原文事实与个人推测分栏；每项关键解释可回到图注或正文；记录图号、页码与来源；未解释的符号明确留作未知。没有核验材料时，先完成前七题，不猜论文图内容。

## 进阶练习：像作者一样做取舍，而不是像描图员一样复制

以下 A–D 题基于已核验的九图种子记录。当前项目还增加了 Eyeriss、RowClone、Plasticine 三篇九图，合计六篇十八图；见 [架构论文对照](../corpus/expert-comparisons.md) 与 [跨组复核](../corpus/synthesis-review.md)。这是有目的的样本，不是行业统计规范。打开原图及相邻正文后作答；来源、页码与逐图证据见 [corpus/README.md](../corpus/README.md) 和 `corpus/figures.json`。这些题目评估设计判断，不要求逐像素重绘。

### A. FireSim 图1与图2：能否合并？

**任务：**写出合并后的收益，以及至少两个可能的误读；再说明你会保留哪些边界、标记。

**参考判断：**合并可能减少来回对照，但容易混淆目标系统与宿主执行资源，也可能混淆目标网络连接与宿主 / 模型连接。若必须合并，需要明确目标与宿主两层、映射关系以及重复实例的数量表达。若一张图塞不下这些信息，分图并非不够高级，而是合理的解释安排。不能只因“少一张图”就删掉层次。

### B. Ray 图4与图6：哪些“统一风格”会破坏意义？

**任务：**有人建议所有边都改成同样的蓝色、同样的细实线，使全篇更统一。请分别指出两图会丢失什么，并提出可行替代方案。

**参考判断：**图4需要保留数据、控制与状态依赖的区分；图6有提交、调度、负载信息的编码，且图注明确线宽表达请求率。统一线条会抹掉信息。可以统一字体、标签密度和边框处理，但保留必要的关系区别；重新编码时必须同步更新图例，不能删掉原语义。图6无数值比例尺，保留线宽含义也不允许从像素宽度估算吞吐量。

### C. AIFM 图4与图5：为什么不全部改成流程图？

**任务：**分别写出必须保留的三项信息，并说出一种错误箭头会暗示的错误事实。

**参考判断：**图4应保留本地 / 远端状态区分、位号或字段边界、字段与标志位解释；其核心是表示格式，不是执行先后。图5应保留全局 / 每核层次、日志类别和对象内部放大的关联；把放大引线改成执行箭头可能误导读者认为对象字段是后续处理阶段。对图5而言，所有箭头强行套用单一“数据流”图例也会混淆链表、指针关联和细节引出。

### D. 用一句“删除理由”证明你真的理解

每张图各选一个候选删减，填写：

```text
我想删除 / 合并：
图的核心主张：
删除后仍能回答的问题：
删除后不能再回答的问题：
因此保留 / 删除 / 移到另一个面板：
需要同步修改的正文或图注：
```

**验收：**不能只说“更简洁”。例如压缩重复对象可以保留层级主张，但必须维持重复范围的表达；删掉边类型图例则可能直接损害依赖解释。允许两种相反决策都通过，前提是清楚交代读者问题与代价，并且没有扭曲原机制。

### E. 用新增真实图反驳自己的“画图规矩”

从 [架构论文对照](../corpus/expert-comparisons.md) 的原论文链接读取对应图与图注，任选两条判断进行反驳，再写一个有前提的新版本：

- “论文一定先总览后细节。”参考反例：Plasticine 图3、4是局部图，图5才到芯片级。修正版：顺序应配合正文论证，不是固定图序。
- “一张图不能有两层抽象。”参考反例：Eyeriss 图1、RowClone 图1使用有关联的局部放大。修正版：避免的是不说明关系的混层，而不是所有多尺度图。
- “框和线越少越好。”参考反例：Plasticine 图3、4保留局部实现细节，RowClone 图4需要状态与电路细节。修正版：检查删后是否还能解释机制，不用固定框数评价。
- “所有新意都要用 NEW 盒子标出来。”参考反例：Eyeriss 图6用数据关系，RowClone 图4用操作和状态变化解释机制。修正版：新意可能在关系、状态或映射，不一定是新增部件。AsterSim 的 `[NEW]` 只是练习5的一种局部表达。

**验收：**指出具体图号和被推翻的绝对措辞；提出保留适用范围的判断。不要把反例再倒过来变成“所以总览必须最后放”之类的新死规矩。

## 统一评分与修订出口

每项 0–2 分：0 = 缺失 / 错误，1 = 部分做到但需口头补充，2 = 独立读者可正确理解。

| 维度 | 2 分的表现 |
|---|---|
| 问题与结论 | 一句话说明读者问题，结论没有超出图和设定 |
| 实体与抽象 | 名称、职责、边界清楚；没有把逻辑模块冒充物理部件 |
| 关系与方向 | 必要关系完整，标签准确，方向与设定一致 |
| 范围与诚实 | 省略、假设、概念顺序或性能限制被明确交代 |
| 可读性 | 标签不被遮挡，起终点明确，最终尺寸可读 |
| 视觉一致性 | 同义同形，图例匹配，去色后核心信息仍在 |

总分只帮助定位问题，不代替语义审查。建议达到 10/12 再整理终稿；**关系方向错误、无依据事实或伪性能结论存在时，无论总分多少都先修订。**“参考答案坐标不同”不扣分；信息正确但布局不同，往往正说明你在理解而非描摹。
