# 体系结构论文的概念图：新生绘图与风格指南

**范围：**硬件框图、微架构细节、数据通路、协议/状态、工作过程、存储布局、软硬件接口；不讨论实验结果曲线、柱状图。面向自己理解机制、与导师讨论以及论文投稿。资料核对日期：**2026-11-01**。

## 先回答：有没有“默认规范”？

有默认的**阅读期待**，没有统一的“体系结构图配色标准”。读者应能辨认组件、边界、方向、信息种类和你的贡献。好图首先是可检验的技术陈述，其次才是漂亮的版面。蓝色不天然代表存储器，红色不天然代表控制，虚线也不天然代表可选路径；你必须定义它们。

本文把四类内容严格分开：

| 层级 | 本文标记 | 如何使用 |
|---|---|---|
| 某年某会议某阶段的规则 | **会务要求** | 投稿该 venue/track/year/stage 时遵守，不能跨年套用 |
| 出版社或学会的制作/无障碍指导 | **出版指导** | 理解原则与生产约束；先确认目标会议是否采用 |
| 为减少歧义采用的表示习惯 | **绘图约定** | 不是标准；一篇论文内固定含义，并用标签/图例说明 |
| 本项目方便起步的参数 | **可选默认** | 可以修改；不代替会务要求，也不声称是文献统计结论 |

## 读起来“成熟”的图，究竟成熟在哪里？

**以下是可检验的专家判断假设，不是“名校/大 lab 的统一风格”，也不是本页已完成的大样本文献统计。**官方格式规则只能保证最低生产条件，不能证明图讲清了机制。没有证据表明某种色板或字体能代表研究者资历。更值得学习的是图如何承担解释责任：

| 候选“潜规则” | 成熟图的可观察信号 | 新生可以立即做的测试 |
|---|---|---|
| **受控抽象** | 同一层级的对象用相近表示；跨层跳转有明确接口 | 随机指一个方框：它是物理组件、逻辑功能还是状态？答案是否稳定？ |
| **稳定语义** | 同名对象跨子图可识别；同一图的同线型不暗中换含义 | 下一幅图若换了图法/箭头语法，有没有明确重新说明？ |
| **选择性强调** | 主次服务本图任务；机制图突出变化，背景图突出定位所需结构 | 读者能否找到本图核心关系？若是方案图，能否指出改变了什么？ |
| **有意省略** | 省略的是当前论证不需要的细节，而非难解释的关键条件 | 省略背压/一致性/仲裁后，图的核心主张是否仍成立？不成立就必须补回 |
| **解释责任明确** | 图支持一项具体主张；边和步骤可逐一核查 | 能否沿图走完一个请求，并说明冲突或失败路径在哪一幅图/哪段正文交代？ |
| **协调多个视图** | overview 负责定位；detail 负责机制；步骤图负责动态过程 | 两幅图是否只是重复美化，还是分别回答不同问题？ |

**判断顺序建议：**技术是否正确 → 是否解释了论文主张 → 是否容易追踪 → 是否能在成品尺寸阅读 → 最后才是视觉个性。这里的“成熟”意味着让读者少猜、让论证可核查，不意味着信息越多越好，也不意味着所有图都要极简。

**证据边界：**本页的会务/出版规则有下列原始来源；以上潜规则是基于机制表达需求提出的设计判断，不由会务规则直接推出。实际样本证据见 [三篇架构论文的九幅图对照](../corpus/expert-comparisons.md) 与 [六篇、十八幅图的跨组复核](../corpus/synthesis-review.md)：前者记录图号、原图观察和例外，后者区分可迁移假设与应撤回的过强表述。这是有目的的小样本，不是全领域频率统计或读者效果实验；不能倒推“所有顶会图都如此”。

**一个重要反例：**样本分析记录 Eyeriss Fig.1 与 RowClone Fig.1 在同一图里通过关联放大桥接多个层级。成熟图不必“一图一层”；应保持同层对象的表示一致，并把跨层的包含、映射或放大关系明确标出。Plasticine 的密集局部图也提醒我们：减少线条不是高于解释机制的目标。评价的是这些选择是否有技术理由。

## 1. 先读规则，再开画布

以下是已核查的 **2026 年具体例子，不是跨会议合规清单**。链接指向原始会务页面。

| 会议与阶段 | 与画图直接有关的已核查内容 | 不要误读为 |
|---|---|---|
| [ISCA 2026 投稿指南](https://iscaconf.org/isca2026/submit/guidelines.php) | 图表应可读；正文须引用图；彩色图须在灰度下可区分。网页列正文 10pt、caption 8pt。 | “图内所有文字必须 8pt”——caption 与图内标签不同 |
| [MICRO 2026 投稿指南](https://www.microarch.org/micro59/submit/guidelines.php) | 同样要求可读、正文引用和灰度区分；正文表列 9pt，caption 至少 9pt；不得压缩模板间距。 | “所有 IEEE/ACM 会议用同一模板” |
| [ASPLOS 2026 CFP：Font Size, Tables, and Figures](https://www.asplos-conference.org/asplos2026/cfp/) | 图/表内文字在文档缩放后一般应看起来至少 9pt，不允许小于 8pt；100% 大小应可读；颜色需照顾色觉差异。 | “源文件中填了 9pt 就合规”——缩放后的实际大小才重要 |
| [HPCA 2026 camera-ready](https://2026.hpca-conf.org/track/hpca-2026-camera-ready-instructions) | 最终稿采用官方 IEEE 模板；PDF 经 PDF eXpress 生成或验证；避免 Type 3 字体，可用 `pdffonts` 检查。 | “这些就是 HPCA 审稿版的全部规则” |

**审稿版 ≠ 最终出版版。** 例如匿名信息、模板选项、页数、版权信息和文件验证流程可能不同。[HPCA 2026 主会页面](https://2026.hpca-conf.org/track/hpca-2026-main-conference)把详细投稿格式指向 HotCRP；本文没有据此推断其审稿版图字号。

**真实的版本陷阱：**核对时 ISCA 2026 网页说明其表格于 2025-11-11 更新，caption 列 8pt；链接的 [sample PDF](https://www.iscaconf.org/isca2026/submit/ISCA2026_sample_paper.pdf) 仍列 caption 最小 9pt，部分页边距也不同。因此不要把下载到的示例视为永不变的权威；遇到冲突，核对最新会务通知并询问 chairs，不要自行挑较宽松数字。这里不替会务裁决冲突。

## 2. 动笔前先写一张“语义草稿”

**绘图约定 / 本项目教学方法。**先填这五项，工具随后再选：

1. **一句主张：**读者看完应该理解什么？例如“新增请求队列把接收与调度解耦”，而不是“展示整个系统”。
2. **范围与抽象层级：**一台主机、一个核还是一个 bank？方框表示物理硬件、逻辑功能还是软件过程？不要在没有解释的情况下把线程、芯片和函数画成同一级。
3. **节点清单：**哪些组件是必要证据？哪些仅提供上下文？图上每个缩写能否在正文或 caption 找到解释？
4. **边清单：**每条边写成“源 → 目的：载荷/事件”。例如 `Core → Queue: request(addr, op)`。如果写不清，不应先画箭头。
5. **省略声明：**例如“仅画读请求；省略一致性流量与背压”。简化是允许的，未说明的简化容易变成错误。

不同问题要选不同图：

| 想解释的问题 | 合适表示 | 最容易误导之处 |
|---|---|---|
| 系统由什么组成、谁包含谁 | 分层框图 | 嵌套框容易被读成物理包含，需说明是逻辑域还是芯片边界 |
| 数据经过什么处理 | 数据通路图 | 连线存在不等于每周期都能并行传输 |
| 请求先后发生什么 | 编号过程图 / 时序图 | 空间从左到右不自动代表时间；需要步骤或时间方向 |
| 状态如何转移 | 状态机 | 节点是状态而非组件；边要写触发条件，必要时写动作 |
| 地址/条目如何组织 | 布局或字段图 | 宽度和位置会暗示位数；不按比例就明确标注 |

## 3. 让线条说技术事实，而不是做装饰

以下是**推荐绘图约定，不是 venue 硬规则**。

- **箭头的语义只选一种。**若表示消息方向，就不要在同图中又用相同箭头表示“依赖于”。不得不混用时，分线型并直接标注。物理双向链路可以一条双向边；请求/响应的载荷或时序不同，通常分开两条更好读。
- **实线、虚线必须有词义。**可以在此图定义“实线：请求路径；虚线：调度控制”。不要同时让虚线表示控制、可选、未来工作三种含义。
- **交叉不等于连接。**优先重排节点/端口减少交叉。若仍有交叉，明确使用接点符号或绕线，并在图例说明“点为连接，无点交叉不连接”。这是一种本地约定，不假设所有读者自动接受。
- **端点比线条漂亮更重要。**线连到哪个队列、端口或流水级必须明确，不能因为对齐方便就接到整块外围。
- **粗细不要无意编码。**粗箭头可能让读者联想到高带宽；若仅用于强调，写清“高亮为本文新增路径，线宽不表示带宽”。
- **重复表示要有数量。**`Bank 0 … Bank N−1` 比三个方框更清楚；若三个只是示意，不要让读者推断恰有三组。
- **图内与正文同名。**不要正文叫 Request Buffer，图中一会儿 RB、一会儿 ReqQ。`B` 与 `b`、`GB/s` 与 `Gb/s` 不可混用；容量是二进制还是十进制要说明。字段区间如 `[31:6]`、地址宽度、队列深度应可核算；不确定的实现参数不要为了好看填数。

### 原创微例 A：从“连起来”到“能解释机制”

**不充分：**`CPU ↔ Cache ↔ Memory`，所有箭头一样，没有边界和范围。这只能说明粗略关系，不能支持“新增 miss queue 改变了请求处理”的主张。

**针对该主张的更好草稿：**

```text
Core ──read(addr)──▶ Cache ──miss request──▶ [NEW] Miss queue ──▶ Memory controller
Core ◀──data─────── Cache ◀──────────────────fill─────────────────┘
```

注解：① `NEW` 文字与高亮冗余，即使没有颜色也可定位贡献；② 请求与返回分开，避免双向箭头掩盖消息种类；③ caption 说明“仅示读 miss；省略 hit 返回与背压”；④ 这只是**逻辑消息示意，不是可直接实现的完整微架构**。不能从此图推出队列深度或周期数。

### 原创微例 B：相同方框，不同语义

`Fetch → Decode → Execute` 可以是功能顺序，也可以被误读成三个各用一周期的流水级。

- 若只谈功能：caption 写“逻辑处理阶段，方框宽度不代表延迟”。
- 若谈流水线：明确寄存器/级间边界；若 Execute 可变延迟，把这个条件写在图或说明中。
- 若谈一次请求的时间线：增加 `t0、t1…` 或有单位的时间方向；不要靠方框间距暗示时长。

### 原创微例 C：颜色不是协议

“红色模块为新增，绿色模块为已有”只靠颜色不够。改成已有模块中性描边、新增模块加 `[NEW]` 标签及更明显边框；颜色仅作辅助。对应 caption 可以是：“新增仲裁器用 NEW 标记；虚线为授予信号；所有请求线为实线。”这比“红色是重点”提供了可复述的技术含义。

## 4. 字体、尺寸和输出：按论文里实际大小判断

### 出版指导的边界

[IEEE Author Center：File Formatting](https://journals.ieeeauthorcenter.ieee.org/create-your-ieee-journal-article/create-graphics-for-your-article/file-formatting/)是**期刊制作指导**：建议图中文字字号与字形一致、成品大约 9–10pt；列出可用字族，并要求 EPS/PS/PDF 字体嵌入或转轮廓。不能据此声称所有体系结构会议只能使用 Times 或 Arial。

[IEEE：Resolution and Size](https://journals.ieeeauthorcenter.ieee.org/create-your-ieee-journal-article/create-graphics-for-your-article/resolution-and-size/)建议可缩放矢量，列出 PDF/EPS/PS；非矢量彩色/灰度图大于 300dpi、黑白线稿大于 600dpi。这些数值属于该出版指导，**不是本项目替所有会议规定的最低分辨率**。

### 你实际该做什么

1. **先决定单栏或跨栏。**宽度从当前模板的 `\columnwidth` / `\textwidth` 取，不把“单栏永远 89mm”写死。
2. **按目标宽度设计标签。**源图宽 180mm、字号 12pt，缩到 90mm 后约为 6pt；源文件显示 12pt 并不能保证可读。缩放公式：最终字号 ≈ 源字号 × 最终宽度 / 源宽度（等比缩放时）。
3. **不靠缩小解决拥挤。**先删与主张无关的结构，或拆成 `(a) overview` 与 `(b) detail`。局部放大框应指向真实对应区域，不虚构空间关系。
4. **保留可编辑源，优先导出矢量 PDF。**SVG 可作为项目源/网页格式，但是否能直接提交由出版流程决定。截图或把 PNG 包进 PDF 不会变成矢量。
5. **字体优先嵌入。**轮廓化是某些流程接受的退路，但会失去可搜索文字和部分可访问性；不要把“全部文字转路径”当无条件最佳实践。保留未转轮廓原稿。
6. **检查最终论文 PDF，不只检查独立图。**看字有没有替换、符号/下标有没有丢失、细线是否消失、箭头是否被裁剪。`pdffonts paper.pdf` 可以查字体嵌入/类型；但通过命令检查不等于视觉合格或自动满足会务要求。

## 5. 色彩与可访问性：去掉颜色，信息仍应成立

**出版指导：**[IEEE 的图形页面](https://journals.ieeeauthorcenter.ieee.org/create-your-ieee-journal-article/create-graphics-for-your-article/)在其线图建议中强调颜色之外的形状/线型、灰度检验与亮度对比。把“冗余编码”用于概念框图是本文的设计延伸，不是 IEEE 指定的框图符号表。[ACM SIGCHI 无障碍指南](https://sigchi.org/resources/guides-for-authors/accessibility/)同样指出只靠颜色区分的图存在障碍；它是 SIGCHI 指导，不应标成 ISCA 的额外强制条款。

- 淡色填充、深色文字适合起步，但“淡”不等于“对比足够”。实际检查文字与背景、线条与背景。
- 最好先画黑白，再给真正需要分组/强调的元素加少量颜色。
- 不给每个模块一种颜色。颜色数量应由**语义类别数量**决定；若图例已经难以记忆，先减少类别。
- 灰度检查与色觉差异模拟不是同一项检查，两者都不能替代真实大小的阅读。
- 不宣称某两个色值天然“色盲安全”：线宽、面积、背景与邻接关系也影响识别。即使配色来自常用方案，也保留文字/线型冗余。

**不仅要看得清，还要可读出：**[ACM SIGACCESS：Describing Figures](https://www.sigaccess.org/welcome-to-sigaccess/resources/describing-figures/)建议文字描述着重图带来的新信息、使用正文术语，不机械重复 caption。适用 ACM 工作流时按模板填写相应 figure description（如 `\Description{...}`）；复杂图可另给结构化说明。

原创示例的描述可以写：“读请求先查 Cache；miss 经新增的 Miss queue 送至内存控制器，返回数据填入 Cache 并回送 Core。图仅表达逻辑消息关系，省略 hit 和背压。”不要写成“图里有四个矩形和蓝色箭头”。图注解释它为什么在论文中，描述补充图具体传达了什么；二者不必重复。

## 6. “像论文图”并不等于“越精致越好”

**本项目建议。**技术图不是电气原理图，也不是营销海报：不要求把所有门电路画出来，但每个保留元素都要服务于理解。

- 默认不用阴影、立体透视、发光、纹理背景；它们可能让相同层级产生虚假的重要性或遮挡关系。若研究确实涉及 3D 堆叠/布局，三维表示可以有技术理由。
- 对齐与均匀间距用于帮助比较，不用于暗示不存在的等时延、等容量或等物理面积。必要时标“not to scale”。
- 背景已有结构弱化但不能弱到不可读；贡献用一个一致的强调通道，不能每个方框都加粗。
- 图例放在使用它的图附近；只有一种连线时不必做庞大图例。能直接标边就不要让读者反复查颜色键。
- 学习论文时模仿**信息组织策略**，而不是照搬图像。复用、改绘已有图需引用并核对许可；自己重画不自动消除归属问题。

## 7. 新手的完成检查单

**语义检查（先做）：**

- [ ] 我能用一句话说出图要支持的主张。
- [ ] 同一层级的对象表示一致；跨层的包含、映射或局部放大关系有明确标记，不把不同层级无说明地并列。
- [ ] 每条箭头能说清源、目的、消息/数据/条件；没有因美观乱接端点。
- [ ] 若图用于说明方案变化，新增结构或改变的关系/操作可辨；没有暗示未经证实的性能优势。
- [ ] 省略了什么、是否按比例、是否表达时序已经说明。
- [ ] 位段、宽度、数量、容量、单位和缩写与正文一致。

**视觉与出版检查（在最终论文中做）：**

- [ ] 单栏/跨栏实际宽度、100% 显示或实际尺寸打印均可读。
- [ ] 去色仍能辨认类别和贡献；色觉差异下也不只靠颜色。
- [ ] 交叉处不含糊；标签不压线；箭头端部和边框未裁剪。
- [ ] 同一术语与角色跨图保持可识别；若另一幅图采用不同箭头语法，用图例/标签重新明确含义，不让读者误沿用。
- [ ] 图在正文被引用，caption 清楚；需要时提供文字描述。
- [ ] 矢量输出/栅格分辨率与字体符合实际出版流程；最终 PDF 已检查。
- [ ] 已复核当前 venue、年份、track 与审稿/最终阶段的最新说明。

## 8. 可直接起步的 house style（仅本项目可选默认）

下面是**教学起点，不是领域标准，也不是自动合规保证**。具体图可按内容改变；本节没有声称项目渲染器已经实现全部选项。

| 项目 | 可选默认 | 调整依据 |
|---|---|---|
| 画布 | 白底；按目标栏宽设计；平面二维 | 确需表达物理堆叠时再使用三维 |
| 字体 | 图内统一一种易读字体，数学符号与论文一致；最终标签先以 9–10pt 为目标 | 目标会务规则、缩放与内容密度；不能仅依赖该区间 |
| 描边 | 最终普通线先用约 0.75pt；强调线约 1.25pt | 实际尺寸打印后细线是否消失；这些不是硬性下限 |
| 方框 | 中性浅填充、深色边框；同层级同圆角/形状 | 用形状编码语义前先定义 |
| 颜色 | 中性灰 + 一种强调色起步；必须有 `[NEW]` / 标签等冗余 | 真有第二类语义再增色；不规定“存储=蓝”等通用含义 |

| 布局 | 主过程左→右或上→下；反馈从外侧绕回；减少交叉 | 时间、空间、拓扑的真实语义优先于整齐 |
