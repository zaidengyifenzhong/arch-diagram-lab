## F4例5 → §7.2 → Table 6：复用的到底是什么？

先看[已有 F4 原图的例5](../gallery/papers/micro-2025-omnisim.md#f4)（[原文p4](https://arxiv.org/pdf/2508.19299v1#page=4)）：控制器先尝试向一个 FIFO 非阻塞写入，失败时再尝试另一个；两个 PE 的处理不同，选路取决于反压。改变 FIFO 深度可能改变查询结果，继而改变功能执行路径，不能只把它看成修改一个与功能无关的容量数字。

接着读 [§7.2（p10）](https://arxiv.org/pdf/2508.19299v1#page=10)，再看 [Table 6／§8.2.3（p12）](https://arxiv.org/pdf/2508.19299v1#page=12)。从初始深度 **(2,2)** 出发，分别试两种修改：

- 改为 **(2,100)**：前次 query 结果的约束仍成立，可以复用已有模拟图并重算时序。复用图不表示目标周期完全不变。
- 改为 **(100,2)**：查询结果改变，旧功能行为不再适用，必须重跑模拟；但已经编译的可执行文件仍可复用，不必连前端编译一起重做。

**练习：第二种情况不能复用图，为什么仍可能比从头开始省时？** 因为“旧图是否仍有效”和“已编译程序是否可继续使用”是两层判断。先标出 Table 6 的约束检查，再区分 FE 前端编译与 MT 多线程执行；不要将增量检查失败写成必须重新编译，也不要将第一种配置的成功推广为任意 FIFO 改动都可复用图。这里仅解释该案例，不转录表中性能数字。

## F2 → §8.1.1／F8：输出、周期和宿主时间各记一栏

[已有 F2](../gallery/papers/micro-2025-omnisim.md#f2)（[原文p2](https://arxiv.org/pdf/2508.19299v1#page=2)）的 toy timer 轮询 FIFO。它的输出虽然叫 `cycles`，仍然是一个功能结果；正确结果依赖目标硬件的 FIFO 访问时序，不能以宿主 OS 调度线程的先后替代。图中真实硬件例子的计数为3，而两种软件调度例子给出不同错误计数。这不意味着整个目标设计的总延迟恰为3周期。

读 [§8.1.1／F8（p11）](https://arxiv.org/pdf/2508.19299v1#page=11)时，用 `fig2_timer` 找到这个 toy timer，再分写四栏：**功能输出／目标周期／宿主端到端模拟耗时／宿主子阶段耗时**。输出正确、周期正确和模拟速度快，需要不同证据；不能拿一个编译或执行子阶段代表整个宿主端到端流程。

v1 的 F8 部分标签写作 `fig3_ex*`，而 Tables 3/4 及正文使用 `fig4_ex*`，存在命名不一致。本导读保留该差异，不擅自将每个柱或标签与 F4 例子逐项配对，也不据此复制实验数值。

## F5 → F6 → F7：理解耦合，而非强行串成同一次执行

[F5（原图）](../gallery/papers/micro-2025-omnisim.md#f5)对应[原文p6](https://arxiv.org/pdf/2508.19299v1#page=6)，先对照功能模拟与性能模拟的关系；再在 [F6（p7）](https://arxiv.org/pdf/2508.19299v1#page=7)读工作流，最后到 [F7（原图）](../gallery/papers/micro-2025-omnisim.md#f7)／[p9](https://arxiv.org/pdf/2508.19299v1#page=9)看线程协同。重点是功能线程何时需要目标时序反馈，性能模拟怎样支撑这一决策。

F6 上下两例以及 F7 不应被写成同一个输入从前到后的连续回放。跨图时先核对设计类型、输入和查询条件；这条阅读顺序用于比较耦合机制，不宣称各图共享一次执行轨迹。
